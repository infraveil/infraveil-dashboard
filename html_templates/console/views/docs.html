Infraveil Development Guide

Understanding the workspace execution environment.

1. Running Long-Lived Services

Infraveil launchers supervise long-running services through a runtime contract. The service command should keep running like a web server, worker, or monitoring process. If it exits cleanly when it was expected to stay alive, the launcher treats that as a supervised process exit and records it for review.

To fix this, wrap your logic in a continuous loop:

import time

def main():
    print("Agent started successfully!")
    
    # Run indefinitely
    while True:
        do_work()
        time.sleep(60) # Sleep for 60 seconds

2. Runtime Manifest & Environment

infraveil.json is the runtime contract. It tells the agent exactly which supervised services to install, build, start, route, watch, and recover across Node, Go, Rust, Java, Python, or any command-line service.

In process mode, the agent extracts the package into a controlled workspace, starts the services from the manifest, and places the Infraveil gateway in front of them so logs, request telemetry, and policy enforcement still work across languages.

config.json and manifest env values are injected as environment variables. Secret references such as infraveil:secret:DATABASE_URL are reserved for managed secret injection. 

{
  "mode": "process",
  "gateway": { "listen": 18443 },
  "services": [
    {
      "name": "node-api",
      "runtime": "node",
      "start": "node server.js",
      "port": 3001
    }
  ],
  "routes": [{ "path": "/*", "service": "node-api" }],
  "persistent_paths": [
    { "path": "data", "type": "dir" },
    { "path": "data/app.sqlite", "type": "file" }
  ]
}
import os

def load_config():
    # Retrieve configuration directly from OS memory
    return {
        "api_key": os.environ.get("api_key", "default_val"),
        "timeout": int(os.environ.get("timeout", 30)),
        "debug": os.environ.get("debug") == "True"
    }

3. Application Output & Logging

Infraveil intercepts standard output without special library imports. In Python memory mode, print() and tracebacks are captured directly. In process mode, stdout, stderr, and process exits are emitted as generic [PROCESS_EVENT] envelopes with service, stream, runtime, exit code, and raw message. These are separated from launcher and agent control evidence on the dedicated App Logs page.

4. Security Pipelines

The Security tab now includes a pipeline builder. This is where you define what the agent should observe, enrich, score, signal, and do next.

What To Capture is the request data you want to keep, label, count, or enrich. Use it for things like / versus /settings, payload shape, country, tenant, feature flag, user-agent family, or session fingerprint.

What To Do is what happens after inspection. Use it to log, score, slow, deceive, block, call your own tool, or hand off to a custom module.

Fast mental model: capture first, act second. If you want to see something in the live dashboard later, it needs to be recorded by your capture side or emitted as a custom signal.

Simple example: if you want to know whether visitors hit /, /settings, or /api/*, add observe_request, tag_route, and count_dimension with dimensions like path, method, and route_group. 

{
  "telemetry_dimensions": ["path", "method", "country", "route_group", "feature_flag"],
  "telemetry_pipeline": [
    { "stage": "observe_request" },
    { "stage": "tag_route", "config": { "map": { "/": "index", "/settings": "settings" } } },
    { "stage": "count_dimension", "config": { "dimensions": ["path", "method", "country"] } }
  ],
  "response_pipeline": [
    { "stage": "risk_score", "config": { "weights": { "scanner": 20, "honeypot": 80 } } },
    { "stage": "block_request", "config": { "threshold": 90 } }
  ]
}

Where custom pipeline logs show up:

1. Pipeline Analytics: this is the main place to inspect request-by-request execution plus the rolled-up analytics summary for your live pipeline output.

2. Network Trace: open any request row and look at Pipeline Telemetry. That is the raw per-request output from your capture and action stages.

3. Security Event Log: use response stages like log_event or actions like block/tarpit/deception when you want a request to create visible security events too.

How to make your own visible fields:

1. Add the field name to Fields To Track if you want it treated like a first-class dimension.

2. Use stage config or module output to write values into telemetry dimensions, custom telemetry keys, or signals.

3. Save the builder, generate traffic, then check the live cards and expanded request telemetry. Your custom keys will show up there if they are actually being emitted.

Rule of thumb: if a request hits your app but you cannot see a value later, the pipeline probably never captured it. Add or adjust a capture stage before trying to debug the action stage.

5. Custom Defense Modules & Tool Contracts

If the built-in stages are not enough, define your own modules and connected tools. Modules describe your runtime logic and any dashboard metadata you want to attach. Connected tools describe internal webhooks or services your pipeline can call.

This is the \"do anything\" layer. You can model SIEM exporters, route classifiers, feature mappers, ticket creators, fraud scorers, deception engines, or company-specific trust systems without waiting for a product update.

Custom module workflow:

1. Give the module a name and trigger family.

2. Put your runtime schema in Schema JSON. This is where you define what the module expects.

3. Put any dashboard-facing metadata in Dashboard/UI contract JSON if you want the module to describe how it should be presented later.

4. Use module output to emit custom telemetry fields or custom signals so the live dashboard has something real to display.

Connected tool workflow:

1. Register a tool under Connected Tools.

2. Give it an input contract with an endpoint and optional method/body shape.

3. Call it from a pipeline stage like call_tool or from your analysis layer.

4. Inspect the request row in Network Trace to verify the tool call and emitted telemetry.

6. Adaptive Analysis Engine

The adaptive engine reads your actual telemetry, security events, and honeypot captures, then drafts pipeline or module suggestions. It is not a chat model. It works from the request stream, captured events, and your configured tool contracts.

Its configuration is fully customizable:

{
  "enabled": true,
  "mode": "draft_pipelines",
  "sources": ["network_trace", "security_events", "honeypot_captures"],
  "allowed_tools": ["suggest_pipeline_stage", "suggest_module", "suggest_honeypot_route"],
  "objectives": ["identify_top_routes", "detect_attack_patterns", "recommend_custom_modules"],
  "custom_tools": [
    {
      "name": "route-intent-classifier",
      "kind": "analysis",
      "purpose": "Group paths into product intent buckets",
      "input_contract": {
        "endpoint": "https://ops.example.internal/classify-route",
        "method": "POST"
      }
    }
  ]
}

The output shows up in the Security Pipeline tab under Adaptive Output so you can see what the engine inferred from real traffic and immediately promote suggestions into the live stack.
